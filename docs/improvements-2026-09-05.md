## 화면과 구조

- 데스크톱은 현재 여정과 행동 버튼을 근거 설명보다 앞에 배치했다. 1280×720 브라우저 검사에서 대체편 버튼이 첫 화면 안에 표시된다.
- 모바일 390px에서 주요 메뉴 5개 모두 가로 넘침이 없다.
- 조회하지 못한 항공·입국·날씨 정보는 0 대신 조회 불가로 표시한다.
- 날짜가 넘어가는 열차 시각에는 다음 날 표시를 붙인다.
- `src/app.js`는 2,277줄에서 약 1,300줄로 줄었다. 화면은 `src/views/journey.js`, `routes.js`, `travel.js`, `validation.js`로 분리했다.
- 여정 계산은 `journey-model.js`, 운행 연결은 `rail-plan.js`, 관광 일정은 `travel-itinerary.js`, 요청 순서는 `api-client.js`, 폼 보존은 `ui-state.js`로 분리했다.
- 같은 여정 입력에서는 계산 결과를 재사용한다. 화면을 열어 둔 동안 출발 시각을 분 단위로 재검사하고, 데이터는 5분마다 갱신한다. 시각에 따라 바뀌는 승차권 안내도 분 단위로 다시 계산한다.
- 기존 CSS의 적용 순서를 유지하면서 파일을 분리했다. 배포 시 한 개의 압축 CSS로 묶는다. 모든 기존 스타일을 새로 설계한 것은 아니며, 후속 화면 변경은 분리된 파일에서 관리한다.
- `npm test`는 현재 앱의 테스트 경로만 실행한다. `check:copies`로 루트와 포트폴리오의 앱 코드 차이를 확인하고 `sync:portfolio`로 반영한다.

## 운영상 남는 조건

공항철도 응답에 역과 구간을 식별할 정보가 없는 경우에는 공식 구간으로 추측하지 않고 체험 연결로 표시한다. 관광 장소의 영업시간을 제공받지 못하면 예상 시간으로 계획하되 확인 필요 표시를 유지한다. 실제 좌석과 예약 처리는 기존처럼 공식 채널에서 확인한다.

공개 Worker에서 유료 AI를 사용하려면 `ENABLE_PUBLIC_AI=true`, API 키와 `PUBLIC_API_RATE_LIMITER` 바인딩이 필요하다. 구성되지 않으면 기본 안내를 제공한다. 운영 키로 유료 요청하거나 실제 파일럿 표본을 등록하지 않았으며, 공개 사이트 배포는 실행하지 않았다.

## 화면 배치 복원과 이미지 요청 개선 — 로컬 수정

사용자가 제공한 개선 전 `desktop-journey.png`와 이전 소스 `ac642b0`를 비교했습니다. 데스크톱에서도 상세 패널을 접고 이동 카드 아래로 옮긴 변경이 기존 정보 순서를 바꿨습니다. 모바일에만 맞춰진 요약 행을 데스크톱에 노출한 변경은 아이콘 크기와 문구 배치가 깨진 원인이었습니다.

- 데스크톱은 제목 → 공항과 철도 조건 → 판단 근거 → 이동 카드 순서로 복원했습니다. 요약 행은 모바일에만 표시합니다. 예시와 실제 조회의 구분, 다음 날 기본 일정은 유지합니다.
- 모바일에서 사용자가 펼친 패널은 재계산과 화면 크기 변경 후에도 유지합니다.
- 기존 공개 화면의 이미지 17개는 `max-age=0, must-revalidate`로 매번 서버 확인을 거쳤습니다. 주요 그림도 자바스크립트 실행 후에야 요청했습니다.
- 작은 SVG 아이콘을 기존 아이콘 생성 스크립트에서 앱 모듈로 함께 생성해 개별 이미지 요청을 제거했습니다. 주요 그림은 HTML에서 미리 요청합니다. 첫 화면의 외부 이미지 요청은 로고와 여정 그림 2개입니다.
- 이미지에는 1시간 캐시를 적용하고, 내용 해시가 있는 앱 번들에는 장기 캐시를 적용했습니다. HTML과 해시 없는 스크립트는 계속 변경 여부를 확인합니다.
- 단위 테스트 68개, 브라우저 테스트 16개, 타입 검사와 빌드가 통과했습니다. 배포용 Worker를 로컬에서 실행해 5개 메뉴를 데스크톱과 모바일로 확인했습니다. 이미지 누락, 가로 넘침, 브라우저 실행 오류가 없었으며 재방문 이미지 전송량은 0바이트였습니다.

위 검증은 사용자가 로컬 수정만 요청한 단계에서 완료했습니다. 이후 최종 검토와 커밋, 푸시, 배포를 요청받아 같은 변경사항의 전체 검사(단위 68개, 브라우저 16개, 타입 검사, 소스 일치, 배포 빌드)를 다시 통과했습니다.

배포 후 실제 주소를 확인하는 과정에서 정적 이미지 응답이 Worker의 캐시 정책을 거치지 않는 차이를 발견했습니다. 빌드 단계에서 정적 자산의 `_headers`에도 같은 이미지 캐시와 정확한 해시 번들 경로의 캐시 규칙을 생성하도록 보완했습니다. HTML과 API에는 이 규칙을 적용하지 않습니다.

공개 호스팅에서 `_headers` 설정도 적용되지 않아, 화면 이미지의 공개 URL을 `/media/`로 연결했습니다. 이 가상 경로는 Worker에서 기존 `/assets/` 파일을 읽고 캐시 헤더를 지정해 응답합니다. 이미지 파일과 디자인은 같으며 로컬 서버에도 같은 경로 매핑을 적용했습니다.
